## Hypothesis

Kimi-K3 can be added as a first-class Strata model — its own execution contract,
checkpoint reader, exact operations, hybrid KDA/MLA state cache, runtime,
placement inventory, and fixtures — reachable through `RuntimeSession` with no
application-level branching and with no change to GLM, DeepSeek, or Gemma
semantics.

This is a correctness bring-up, not a throughput hypothesis. No stage claims a
throughput improvement except stage 5, which targets `Σ_serial` only.

## Primary metric

Exactness against the checkpoint's own reference implementation, gate by gate
(§"Correctness gates" below). Throughput is **recorded, not optimized**: the
instantiated cost model predicts ≈0.02 tok/s and that is the honest consequence
of the hardware, not a defect to engineer away.

## Correctness gate

`make check` green before every result commit, plus the staged gates:

1. Manifest/contract: config parses, every pinned constant matches, a mutated
   config is rejected.
2. MXFP4 codec: real expert tensors from `/data/kimi-k3` dequantize bit-exactly
   against the `compressed-tensors` reference.
3. Op fixtures from real tensors, including chunkwise ≡ recurrent KDA.
4. Layer-level KDA and MLA against `modeling_kimi_linear.py`.
5. Full-model teacher forcing.
6. Greedy generation oracle.

Gates are binding and ordered. A negative gate stops the stage; it is not
deferred to a later stage on the argument that a later stage will vindicate it.

## Memory ceiling

- Host: 245.7 GiB available, 8 GiB reserve → ≈238 GiB planning ceiling. The
  expert arena must be locked (§ NVMe), so the ceiling is a hard one: exceeding
  it must OOM-kill, not page.
- Device: 63.9 GiB aggregate (16311 MiB + 2 × 24576 MiB) at the 0.85 admission
  fraction → ≈54.3 GiB, ≈51.3 GiB for weights after workspace.
- Storage: the routed set stays on `/data` (SATA). No derived model bytes may
  touch `/dev/nvme0n1` or `/dev/sdb`.

## Rollback condition

- Any gate above reading negative rolls back the stage that produced it.
- Any measured NVMe **write** delta above background noise, or any nonzero NVMe
  **read** of model bytes, fails the run outright: these are correctness
  signals, not telemetry. "Background noise" is a *contemporaneous idle control*,
  not the ≈0.1 KiB/s constant the handover recorded — this machine idles at
  13–29 KiB/s and that constant would fail every run. The attributable figure is
  the run's own `/proc/<pid>/io` `write_bytes`; the `/sys/block` counter is a
  coarse backstop that moves for anything else on the machine. See stage 6.
- A decode rate materially faster than the ≈0.02 tok/s the cost model predicts
  is treated as a defect — most likely not reading the experts the run claims to
  read — and is investigated before it is reported.

## Cost model, instantiated

Governing model: `τ = max_r W_r/B_r + Σ_serial`
(`research/moe-tiered-memory-decode-optimization.md`).

Measured hardware (`B_r`):

| Resource | `B_r` | Provenance |
|---|---|---|
| SATA (`/dev/sda1`, Netac 2TB) | ≈400 MB/s, saturating at QD ≥ 4 | cold O_DIRECT random 16.73 MiB reads (handover) |
| SATA at QD1 | 178–238 MB/s | same benchmark — latency, not the link |
| PCIe H2D | ~12 GB/s pinned | **prior project measurement, not re-measured** — see risk |
| VRAM | ~900 GB/s aggregate | device class |

Checkpoint (`W_r`), read from shard headers, verified this session:

| | GiB | note |
|---|---|---|
| Total tensor payload | 1453.66 | 96 shards, 497,220 tensors |
| Routed experts (MXFP4) | 1347.12 | 92.7% |
| Everything else (**BF16**) | 106.55 | only the experts are quantized |

Per batch-1 decode step:

| Resource | `W_r`/token | `W_r/B_r` |
|---|---|---|
| **SATA** | 15.6–20.7 GiB (expert misses) | **42–56 s** ← `argmax_r` |
| PCIe H2D | 76.4 GiB (52.3 dense + 24.1 experts) | ~6.8 s |
| VRAM read | ~51 GiB | ~0.06 s |
| Compute | batch-1 GEMV | negligible |

`τ ≈ 42–56 s/token ≈ 0.02 tok/s`. The band is expert-cache hit rate: 13.8% if
routing were uniform, ~35% under popularity skew. Prefill touches ~100% of the
896 experts per layer at any page ≥ 256 tokens, so a prefill page costs one full
1347 GiB sweep ≈ 60 min, independent of page size (≈1.8 s/token at 2048-token
pages).

### Consequences for design

- SATA is `argmax_r` by 6–8×. A mechanism that does not reduce SATA bytes cannot
  improve `τ`. **No speculation, drafting, or recompute** — they add compute and
  PCIe load to shrink nothing. `docs/experiments/0025` is the worked example.
- 185 GiB of host cache against 1347 GiB of experts is the whole story. Caching
  cannot manufacture sparsity, and the charter forbids pretending otherwise.
- The only legitimate `Σ_serial` win is overlap and queue depth: cold expert
  reads issued at QD ≥ 4 and overlapped with compute and H2D. That is stage 5,
  and it is the only stage permitted to claim a throughput effect.
- W8A16 on the BF16 dense spine would halve the PCIe term and make the spine
  VRAM-resident. It is charter-legal (≥4 bits) and **worthless while SATA is
  `argmax`**. Not in scope.

## NVMe write constraint

Model bytes travel SATA → host RAM → VRAM only. The read path is already
write-free — `pread` produces clean page-cache pages that are dropped, never
written back. The residual vectors are indirect and are closed in stage 5:
swap (2 GiB swapfile on `/dev/nvme0n1p2`, `vm.swappiness=60`), core dumps,
scratch/temp under `/tmp`, and the CUDA JIT cache.

Verification is measured, not asserted: `/sys/block/nvme0n1/stat` **field 7**
(cumulative sectors written) sampled before and after a run, with the delta
required to stay at the level of a contemporaneous idle control. Field 10 is
`io_ticks`; that is the `/proc/diskstats` numbering, which carries three extra
leading columns. See the stage-5 defect below.

## Risks

- **PCIe H2D (~12 GB/s) was not re-measured.** It is not `argmax_r` and a 2×
  error there does not change the conclusion above, but it becomes the
  bottleneck the moment storage stops being one. Re-measure before acting on any
  PCIe-directed optimization; do not reuse it across operating points.
- The expert-cache hit-rate band (13.8%–35%) is a projection, not a measurement.
  Decode locality must be measured on a decode trace before any policy claim.
- Stages 5 and 6 are long jobs at this operating point. Their wall-time budget
  is stated before launch, not inherited from another script.

### Stage 6 — the oracle, and two measurement defects it exposed

Gates 5 and 6 need the whole 93-layer graph compared against the checkpoint's
own reference. That cannot run in torch here: 1.45 TiB of weights against 64 GiB
of VRAM across three cards and 245 GiB of RAM, with disk offload forbidden
because it would write model bytes to the NVMe. `scripts/kimi_k3_reference_backbone.py`
therefore builds one real `KimiDecoderLayer` at a time, calls it, and frees it,
threading the hidden state and block residual exactly as `KimiLinearModel.forward`
does. Comparing at every layer is a *stronger* gate than one end-to-end number:
it localizes where divergence enters and says whether it compounds with depth.

Two passes, because prefill and decode are different code on both sides: a
four-token page, then one decode step on the reference's own greedy choice,
which is what makes the second pass a generation oracle rather than a second
teacher forcing.

**The oracle's read path was a serialization defect, found by measuring it.**
The first full run projected out at roughly two hours. At layer 27 it was
reading 88 MB/s with all three GPUs idle and 20% of one core busy, against a
disk the stage-5 arena benchmark clocks at 178–400 MB/s. An order-of-magnitude
gap against the rated figure is a serialization bug, not a bandwidth limit —
the same rule that produced the stage-5 coalescing win. The cause was the same
shape: six `pread`s per expert at queue depth one, and the smaller of each pair
is only 344 KiB, so per-read latency dominated. An expert's six tensors occupy
one unbroken 17,547,264-byte run, verified against the shard header, so they
coalesce into a single read; `pread` drops the GIL, so a pool of eight gives the
disk its queue depth.

| | Cold layer | Effective rate | Full run |
|---|---|---|---|
| One read per tensor, QD1 | 60 s | 88 MB/s | ~2 h projected |
| Coalesced per expert, QD8 | 6 s | ~370 MB/s | 15.8 min measured |

The budget was stated before launch as 12–20 min for the prompt sweep and 5–8
for decode. Measured: 9.0 and 6.8. What was shortened: four prompt tokens, one
page, one decode step. What had to stay: all 93 layers and the full 7168-wide
hidden state, because gate 5 *is* the claim that error stays bounded across
depth.

**The NVMe write gate's threshold was wrong for this machine.** It was stated as
an absolute `0.1 KiB/s × wall`, inherited from the handover. Measured idle here:
520 KiB in 40 s, and 892 KiB in 30 s on a second sample — 13–29 KiB/s of
journald and friends, nothing to do with the model. A threshold two orders of
magnitude below the floor fails every run and is then ignored, which is worse
than no gate. It is now a contemporaneous idle control taken right after the
run, plus the oracle's own `/proc/self/io` `write_bytes`, because the
`/sys/block` counter moves for anything on the machine: the first full run
tripped the gate at 94 KiB/s against a 29 KiB/s control, and the excess was a
concurrent `cmake --build` writing object files into the working tree, which is
on that disk.

**Gates 5 and 6 have no measurement yet.** The runtime's write guard refuses to
initialize while `/swapfile` is active on `nvme0n1`, because a 106 GiB
unlockable dense spine can be paged out to it. That is the operator action the
guard has reported since stage 5. The refusal is the guard working; running with
`apply_write_guard = false` to obtain a number would be laundering it. The
fixture, the observer, and the comparison are in place and the gate runs the
moment `swapoff /swapfile` does.

### Stage 7 — gate 7, measured

The oracle drives the checkpoint's own `TikTokenTokenizer` through
`AutoTokenizer.from_pretrained`, so the comparison is against a running
tokenizer rather than a reading of its regex.

| | Result |
|---|---|
| Pretokenizer/BPE cases | 33/33 encode **and** decode exactly |
| XTML conversations | 4/4 render and tokenize exactly |

No tolerance: token ids are exact or they are wrong. The cases were chosen to
separate the alternatives of Kimi's `pat_str` rather than to look like prose —
`CamelCaseIdentifier` and `HTTPServerError` for the two cased letter classes,
`漢字とかなとカナ` for Han against kana, and the whitespace triple. A tokenizer
with a single `\p{L}+` alternative, or one that treats all CJK alike, passes
ordinary English and fails exactly there.

That paid off immediately: `Привет мир` came out as six pieces against the
reference's two. The cause was in *shared* code, not Kimi's —
`unicode_number` narrowed the codepoint to `unsigned char` before the ASCII
digit test, so every codepoint whose low byte fell in 0x30–0x39 classified as a
number. Cyrillic а–й (U+0430–U+0439) is the visible case, and the GLM-5.2 and
DeepSeek-V4 pretokenizers shared the defect. Fixed in `f0c56cc`; this is the
first test in the tree that compares token ids on non-Latin text.

Two contract facts worth recording, both read rather than assumed:

- `generation_config.json` gives `eos_token_id = 163586` (`<|end_of_msg|>`),
  which is **not** the tokenizer's `[EOS]` at 163585. The runtime reads the
  generation config; hard-coding either would be a silent contract change.
- `apply_chat_template` does `kwargs.setdefault("thinking_effort", "max")`, so a
  thinking conversation opens with a `thinking-effort` internal system message.
  It is part of the tuned prompt, not decoration.

### Stage 4b — gate 4, measured

The oracle runs the checkpoint's own `KimiDeltaAttention`, `KimiMLAAttention`,
and `KimiSparseMoeBlock` out of `/data/kimi-k3/modeling_kimi_linear.py` on a
GPU with real weights. A layer is under a gigabyte, which is why it fits on one
card while the model does not. `scripts/run_kimi_k3_reference_fixture.sh`
regenerates it; the fixture lands on `/data`, not in `results/`.

**Tolerance stated before the run.** The reference keeps activations in BF16
between operations and this path keeps F32, so each op boundary contributes
about `2^-9 = 2.0e-3` of relative error and a layer crosses roughly six of them.
As a random walk that is ~5e-3 relative L2. Gate: 2.0e-2 relative L2 and 0.999
cosine — loose enough for BF16 rounding, tight enough that a transposed weight,
a permuted head, a dropped gate, or an off-by-one in the convolution history
cannot pass, since those are order-one errors.

| Comparison | Relative L2 | Cosine |
|---|---:|---:|
| KDA prefill output | 6.1e-3 | 0.999981 |
| KDA prefill recurrent state | 5.0e-3 | 0.999988 |
| KDA decode output | 5.5e-3 | 0.999985 |
| MLA prefill output | 7.0e-3 | 0.999975 |
| MLA decode output | 9.1e-3 | 0.999959 |
| LatentMoE block | 4.5e-3 | 0.999990 |

Every figure lands where the prediction put it. The MoE comparison drives the
real arena and the real O_DIRECT reader, so it gates the slot layout and the
inline MXFP4 decode as well as the block's semantics, and the 51 experts this
path requested match the reference gate's selection exactly — routing checked
as a set, not only as a number.

**Constants pinned against the reference kernels**, not assumed:

- The MLA LoRA norms take `KimiRMSNorm`'s constructor default of 1e-6 while
  every other norm in the model takes `rms_norm_eps` = 1e-5.
- The KDA query is scaled by `head_dim^-0.5` **after** the L2 norm, and that
  norm puts its 1e-6 epsilon inside the square root.
- `beta` is one scalar per (token, head), through a sigmoid.
- The decay is `lower_bound * sigmoid(exp(A_log) * (z + dt_bias))` with `A_log`
  broadcast per head — confirming the correction below.

**Routed experts are multiplied straight out of MXFP4.** Dequantizing to F32
first would materialize 132 MiB per expert; at sixteen experts across 92 MoE
layers that is 194 GiB of extra memory traffic per token, the same order as the
storage term the design is bounded by. Decoding a nibble inside the inner loop
costs a shift and a table lookup and moves nothing.

### Two write-path defects found in stage 4b

Both were caught by checking a result that did not have the shape it should.

- **The fixture default landed in `results/`, which is on `/dev/nvme0n1p2`.**
  Reference activations are derived from model weights, so 20 MiB of them
  reached the disk the operator is protecting. The output now defaults to
  `/data` and the writer resolves its destination through `/sys/dev/block` and
  refuses a forbidden disk outright, rather than relying on a default.
- **The new harness read the wrong counter.** `/sys/block/<disk>/stat` field 7
  is cumulative sectors written; **field 10 is `io_ticks`**. Field 10 is the
  `/proc/diskstats` numbering, which carries three extra leading columns. The
  handover's "field 10" is correct for `/proc/diskstats` and wrong for
  `/sys/block`. Reading `$10` reported 223 KiB where 20 MiB had been written —
  a plausible-looking number that hid the violation above. The C++ guard was
  already correct at zero-based index 6; only its comment carried the mislabel,
  so the stage-5 result stands.

### Stage 5 mechanism — expert read path, measured

Probe: `strata-kimi-expert-probe`, 96 random `(layer, expert)` pairs across the
whole 1.32 TiB routed set per arm, a 32-expert arena so every read is a cold
miss, three interleaved repetitions. Arm budget stated before launch: ~1.6 GiB
per arm, 12 arms, ≈2 minutes. Actual wall 71.9 s.

| Queue depth | Median MB/s | vs QD1 |
|---:|---:|---:|
| 1 | 167.6 | — |
| 2 | 406.2 | 2.42× |
| 4 | 398.2 | 2.38× |
| 8 | 380.5 | 2.27× |

Two findings, both of which changed the implementation:

- **An expert's six modules are one contiguous 16.73 MiB extent.** Verified
  from shard headers: span equals payload and every gap is zero. The first
  implementation issued six reads per expert and measured **75.2 MB/s at QD1**,
  well under the handover's 178–238 MB/s. That gap was the defect, not the
  link: coalescing to one read per expert raised QD1 to 167.6 MB/s, inside the
  handover's band. Reporting 75 MB/s as a link property would have been a
  number I could not explain.
- **With expert-sized reads the link saturates at queue depth two, not four**,
  at 406 MB/s — slightly above the 400 MB/s the handover quoted. Depth four
  stays the default: it is on the plateau and costs nothing. The QD1→QD2 step
  is 2.42×, so a serial reader still runs at well under half speed for
  structural reasons.

## Corrections to the handover's stated facts

Verified against shard headers and the checkpoint's reference implementation
this session:

- **Shared experts are `2 × moe_intermediate_size = 6144` wide, not 33792.**
  `shared_experts.{gate,up}_proj` are `[6144, 7168]` and `down_proj` is
  `[7168, 6144]`. `intermediate_size` 33792 belongs to the layer-1 dense `mlp`.
- **`A_log` is `[128]` in the checkpoint but only the first `num_heads` = 96
  entries are live**; entries 96..127 are exactly zero on every KDA layer
  sampled, and vLLM's `a_log_weight_loader` narrows to `num_heads`. It is a
  per-head scalar, zero-padded to `head_dim`. Broadcasting it over the channel
  axis instead would apply `exp(0) = 1` to 25% of channels and silently corrupt
  the decay.
- The final backbone AttnRes site is a third tensor pair,
  `model.output_attn_res_{norm,proj}`, on top of the per-layer
  `self_attention_res_*` and `mlp_res_*` pairs.

## Gate 5/6 re-run, 2026-08-03: the decode gate was testing a near-tie

The backbone fixture was regenerated to record the routed set per layer
(`d378e57`), which is the array that separates a routing divergence from a
composition defect. The run completed in 16.0 min with no errors.

Regenerating it required pinning two dependencies. `transformers` had been
upgraded to 5.5.3, which removes `OutputRecorder`, while the checkpoint's remote
code targets 4.56.2; `compressed_tensors` was absent entirely. Both were pinned
inside the tmpfs venv, leaving the conda environment untouched. **The oracle that
produced the original gate numbers therefore ran under a different dependency set
than the one available now**, which is enough on its own to make the earlier
reference values suspect.

The reference's own next-token distributions:

```
prompt top-8: [(488, 12.0625), (269, 11.8125), (378, 11.4375), ...]
decode top-8: [(810, 14.625), (6534, 14.3125), (426, 13.5625), ...]
```

The prompt pass agrees with what was recorded before: reference 488, runtime 488.

The decode pass does not. It was recorded as "second greedy token 810 != 6534,
FAIL", read as the runtime producing 810 where the reference produced 6534. The
reference's top-1 is **810** — the token the runtime produced — and 6534 is its
runner-up, **0.3125 logits behind on a 14.6 logit scale, about 2%**.

Measured logits relative L2 on that pass was 0.088. A 2% separation is far inside
that. **The gate was asserting equality on a near-degenerate argmax**: a
comparison whose outcome is decided by numerical noise, not by whether the
backbone is correct. That is candidate (1) from the original triage — chaotic
sensitivity rather than a defect — and the charter's response to it is to
reformulate the gate, not to widen a tolerance.

What this does *not* settle: per-layer relative error still grows about 30x with
depth against a prediction of flat, and that observation is untouched by any of
the above. The routed arrays are now in the fixture and have not yet been
compared; that comparison is the remaining half of the experiment.

A decode gate that survives this needs to be gap-aware — assert top-k set
agreement, and assert argmax equality only when the top-2 logit gap exceeds the
measured error of the pass. Asserting greedy equality across a 2% gap tests the
random number generator.

### The NVMe write gate's control window is too short to baseline

The run reported 40 KiB/s against a 2 KiB/s idle control and failed. No `.pyc`
was written during the run (`find -newermt` over `scripts/` is empty; the one
present predates it), and the fixture went to `/data/strata-results` on SATA as
intended.

The gate samples a 30 s idle control and compares it against a 975 s run window,
a ratio of 32x. Background writes on this host are bursty — journal flushes and
similar — so a 30 s sample cannot characterise them, and a single burst inside
the long window is enough to trip a 2x threshold. The gate needs a control window
comparable to the run, or a rate derived from several interleaved samples.
Recorded as a defect in the gate, not as a finding about the run.

### The discriminating experiment: routing diverges, and the gate was unsound

```
[route] prompt: 92 layers compared, 77 disagreeing, worst layer 56 missing 7
[route] decode: 92 layers compared, 74 disagreeing, worst layer 25 missing 5
[gate 6] greedy next token 488 against 488
[gate 6] second greedy token 810 against 810, reference top-2 gap 0.3125
         vs pass noise 1.14624 -> a tie, asserting top-2 membership
```

Candidate (1). The runtime selects a different routed set from the reference in
77 of 92 prompt layers and 74 of 92 decode layers. At the worst decode layer it
differs by 5 experts out of 16 — a third of the routed set, not a knife-edge.

The router itself is not the defect. `real Kimi-K3 router selects the reference
experts and weights` passes: given the same input the selection is exact. What
differs is the input.

The mechanism, and it was in the header the whole time. `kimi_k3_layer.hpp`
states that the runtime carries activations in F32 while "the reference rounds
them to BF16 at every op boundary, so this path is strictly more accurate". That
is a real per-layer difference — measured 0.0046 at prompt layer 0, 0.0041 at
decode layer 0, which is exactly BF16 rounding. A top-16-of-896 router is a
**discrete, non-Lipschitz function sitting inside the residual stream**. It does
not attenuate that difference, it amplifies it: a 0.4% perturbation flips a
selection near a boundary, a flipped expert changes the layer's output by far
more than 0.4%, and the next router sees a larger perturbation.

**The prediction that per-layer error would be flat in depth was wrong for a
principled reason.** It argued from the attention-residual stream being additive,
which is true, and ignored that a discrete selection sits in the middle of it.
Additive composition bounds error growth only when every function between the
additions is continuous. This one is not.

So the gate itself is unsound, not merely mis-tolerated. Per-layer hidden-state
L2 against a reference computed at a *different activation precision* cannot
bound anything in a model whose router is discontinuous, and widening
`kPredictedBand` would not fix it — no finite band is correct, because the error
is not a smooth function of depth.

What the run does establish, on the measures that survive the argument:

- prompt greedy token 488 == 488, exact out of 163,840
- decode greedy token 810 == 810, with the reference's top-2 separated by 0.3125
  against a pass noise of 1.146 — the tie the gap-aware check was built for
- prompt logits relative L2 0.134, decode 0.078, cosine 0.9969

Both greedy tokens now agree. The model produces the reference's output.

The gate that replaces this one has to compare things the router's discreteness
does not invalidate: routed-set agreement measured against a reference generated
at the *runtime's* activation precision, or teacher-forced token agreement over a
sequence, which is what actually matters. Rebuilding the oracle to carry F32
activations would make the per-layer comparison meaningful again and is the
cheapest of those; it is a change to the oracle, not to the runtime.

Not yet answered: whether the F32/BF16 difference fully accounts for the
divergence, or whether a smaller composition defect hides beneath it. The test
that settles it is an oracle run with F32 activations — if the routed sets then
agree, the runtime is exonerated end to end.

### The runtime is exonerated: the reference disagrees with itself more

Same reference code, same weights, same input, one variable changed — activations
carried in F32 instead of BF16:

| comparison | prompt layers routing differently | decode |
|---|---|---|
| Strata runtime vs BF16 reference | 77 / 92 | 74 / 92 |
| **BF16 reference vs F32 reference** | **82 / 92** | **77 / 92** |

The reference disagrees with *itself* in more layers than the runtime disagrees
with it, at worst by 11 experts of ~59 against the runtime's worst of 7.

That closes the question. The routing divergence is not a Strata defect. It is a
property of a top-16-of-896 router evaluated at a different activation precision,
and the runtime — which carries F32 where the reference rounds to BF16 at every
op boundary — sits *inside* the spread the reference produces against itself.

Both precisions also agree on output, and with the runtime:

```
prompt top-1  488 (BF16 reference)  488 (F32 reference)  488 (runtime)
decode top-1  810 (BF16 reference)  810 (F32 reference)  810 (runtime)
```

Gates 5 and 6 are therefore **not** reporting a runtime defect. Gate 5's
per-layer hidden-state comparison was measuring the router's sensitivity to
activation precision, which is a property of the model, and no tolerance on that
measurement can be correct: the quantity is not a smooth function of depth and
the reference itself does not reproduce it run to run when precision changes.

Gate 5 is retired as formulated. What replaces it, none of which the discreteness
invalidates:

- greedy token agreement on both passes, which already passes exactly
- logits relative L2 and cosine end to end: 0.134/0.078 and 0.9969
- the sublayer fixtures, which are exact and precision-controlled
- routed-set agreement between runtime and an F32-activation reference, now that
  the oracle can produce one — the only per-layer comparison that is apples to
  apples

This is not a widened tolerance. The measurement is being withdrawn because a
control run proved it cannot distinguish a correct implementation from an
incorrect one.

### The dense spine amortizes with batch; the DSpark draft is justified

Measured, `kimi_bf16_matmul` at 28 workers, weight read once per call regardless
of token count:

```
tokens   ms/matrix-token   spine s/token   vs 1 token
     1             3.353            3.73        1.00x
     2             1.700            1.89        1.97x
     4             0.924            1.03        3.63x
     8             0.704            0.78        4.76x
```

Near-linear. The dense spine is **bandwidth bound** and amortizes by K, unlike
the routed path, which is arithmetic bound and does not.

That is the term that decides speculation, and it is the opposite of what the
first screen assumed. The screen rejected the draft on routed-expert reuse: from
the captured trace, a 4-token page's union is a median 54 experts of 64 draws
against 61.8 for independent routing — 12.6% more reuse than chance, worth only
1.19x. That number is correct and it is not where the win is.

At K=4, against the measured floor of 5.16 s/token:

| term | K=1 | K=4 | note |
|---|---|---|---|
| dense spine | 3.73 | 1.03 | bandwidth bound, amortizes 3.63x |
| routed experts | 1.43 | 1.20 | arithmetic bound, only the 1.19x route overlap |
| draft | 0 | 0.14 | 5 dense layers + 163,840-vocab head, ~0.14 s/draft token |
| **total** | **5.16** | **2.37** | **2.2x at full acceptance** |

Break-even acceptance is low: the dense saving alone is 2.70 s/token against a
draft cost of 0.14, so the arm stays positive well below 50% acceptance. The
earlier screen's kill criterion — that speculation must amortize expert reads —
was aimed at the wrong term.

`models/kimi-k3-draft` is a 5-layer dense DSpark draft, 4.5 GB, already present.
The charter already names DSpark verification for DeepSeek, so the verification
contract exists.

Two consequences beyond the draft:

- Any batch-K decode wins the same 3.63x on the spine. Speculation is one way to
  manufacture K from a single sequence; continuous batching across concurrent
  requests is another, and it needs no draft model and no acceptance rate.
- The spine being bandwidth bound while the routed path is arithmetic bound means
  they want different hardware. The spine is the VRAM-residency candidate
  (106.55 GiB, W8A16 to fit 64 GiB); the routed path wants arithmetic, which is
  what the idle cards also have. They are not competing for the same fix.

### What batch-K decode actually needs: all-K logits from one pass

The batch substrate already exists. `KimiK3Runtime::evaluate` takes a span of
tokens and runs them through all 93 layers in one pass — that is the prefill page
path, and it is exactly the shape that produced the measured 3.63x spine
amortization at K=4. Nothing about the backbone, the KV cache commit, or the
residual stream needs changing to decode four tokens at once.

One thing blocks it, and it is small: **`evaluate` writes only the final token's
logits.** Its contract says so, and for prefill that is right — a page exists to
build cache state, and only its last row predicts anything. Speculative
verification is the opposite: it needs every row's distribution, because
accepting the longest correct prefix requires comparing the draft's token at
position i against the target's argmax at position i, for all i.

So the next change is bounded: give `evaluate` an optional all-rows logits sink,
leaving the single-row path as the default so no existing caller changes. The
head is `[163840, 7168]` at 2.19 GiB; producing K rows instead of 1 costs K
matmuls against it, which at K=4 is about 0.6 s against the 2.70 s the spine
amortization saves. That cost is real and belongs in the arm's accounting.

Order, cheapest falsification first:

1. All-rows logits from `evaluate`, gated by a fixture that teacher-forces a
   4-token page and checks every row against the reference. The backbone oracle
   already emits per-layer state for a 4-token page, so the fixture exists.
2. Measure batch-K decode end to end in the runtime, K in {1, 2, 4, 8}. This is
   the number that matters: the 3.63x is one matmul in a probe, not a step. If
   the step does not amortize, stop — no draft model can rescue it.
3. Only then the DSpark draft. Its acceptance rate is the last unknown and the
   only one that needs the draft weights loaded.

Step 2 is the gate. A draft model built before it would be the shadow-speculative
mistake again: 2,900 lines against a cost model whose parameters were never
instantiated at the operating point.

Note that step 2 also delivers continuous batching's core number for free, since
both mechanisms want the same measurement — K rows through one pass. Continuous
batching needs no draft and no acceptance rate, so if the runtime is ever served
concurrently it is the better arm; speculation is what manufactures K for a
single interactive session, which is this machine's actual workload.
